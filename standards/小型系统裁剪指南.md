# 内网自研系统规模分级与裁剪指南

| 项目 | 内容 |
|---|---|
| 文档编号 | STD-AI-002 |
| 版本 | v1.0（评审稿） |
| 上级文档 | STD-AI-001《内网 AI 开发技术栈标准》 |
| 生效日期 | 随上级文档 |
| 适用范围 | AI BP 团队所有内网自研系统的规模定档与组件裁剪 |
| 归口部门 | 数字化 / IT |
| 标准负责人 | 架构负责人 |
| 评审周期 | 与 STD-AI-001 同步（每季度） |

> 一句话：**技术基线不因为系统小就改变；改变的只是"装多少组件、做多严的演练、留多少证据"。裁剪必须显式登记，不允许"小系统就自由发挥"。**

---

## 0. 为什么需要这份指南

STD-AI-001 给出的是**统一基线**，但基线是按"内网自研系统的最大公约数"写的：它假设你可能要调模型、可能要跨进程共享、可能有多实例。现实中大量需求只是一个部门十几个人用的台账/审批/看板类系统。把基线原样套到这类项目上，会出现三种可预期的失败：

| 症状 | 表现 | 根因 |
|---|---|---|
| **过度建设** | 20 人的系统照抄基线，单机跑 Nginx + .NET + SQL Server + Garnet + Python 侧车 + AiGateway + Ollama 七个进程，内存互相挤，没人说得清哪个是必需的 | 缺"哪个组件在什么规模下才需要装"的判据 |
| **借小摆烂** | 以"内部小工具"为由不写 `deploy.ps1`、迁移脚本不入库、不做越权校验、不配密钥扫描；半年后原作者转岗，系统没人敢动 | 缺"哪些条款与规模无关"的红线清单 |
| **ADR 通胀** | 装或不装 Garnet、加不加一个 NuGet 包都提 ADR 排队评审，评审人疲于签字，最后大家绕过流程先做了再说 | 缺"档内裁剪免评审"的登记通道 |

本指南解决这三件事：**§1 定档 → §2 红线 → §3 分档矩阵 → §7 登记方式 → §8 升档触发**。

## 1. 规模定档

### 1.1 三轴判据

**取最高档**：任一轴命中高档，整体定高档。不允许"按用户数定 S，但因为有 AI 就顺便自己加几个组件"。

| 判据 | S（小型） | M（中型） | L（大型） |
|---|---|---|---|
| 注册用户数 | ≤ 50 | 50 – 500 | > 500，或跨部门强数据隔离 |
| 峰值并发（同时在线） | ≤ 10 | ≤ 50 | > 50 |
| 日请求量 | < 5 万 | 5 – 50 万 | > 50 万 |
| 业务数据量（3 年累计，不含附件） | < 5 GB | 5 – 100 GB | > 100 GB |
| 是否调用大模型 | 否 | 是（只读问答 / 内容生成） | 是（Agent 多步、带工具调用） |
| 是否写回外部生产库（MES/ERP/WMS） | 否 | 否（只读集成） | 是 |
| 是否需要多实例或零停机 | 否 | 视情况 | 是 |
| 是否有附件/文件存储 | 可选 | 通常有 | 通常有，需配额与生命周期 |

### 1.2 判定流程

```
需求到手
   │
   ├─ 会调用任何模型吗？ ──── 是 ──▶ 至少 M 档（且必须经 AiGateway）
   │                                └─ 涉及工具调用/多步 Agent ──▶ L 档
   │
   ├─ 会写回外部生产库吗？ ── 是 ────────────────────────────▶ L 档
   │                                └─（只读取数 → 记为"只读集成"，不升档，
   │                                     但必须写清数据源/频率/字段映射/对账）
   ├─ 注册用户 > 50 或 峰值并发 > 10？ ── 是 ──────────────▶ M 档
   │                                └─ 需要 ≥2 实例或零停机 ──▶ L 档
   │
   └─ 全部为否 ─────────────────────────────────────────▶ S 档
              （在 README 登记裁剪声明，走 §3 的 S 列，免 ADR）
```

> 判据用**可数的量**（人数、并发、数据量、是否），不用"重要性""复杂度"这类无法在评审时对齐的词。

## 2. 永不裁剪清单（任何档位都是红线）

这一节是"借小摆烂"的解药。以下条目**与规模完全无关**，S 档不得以"人少、事小、内部用"为由豁免：

1. **五条铁律**（STD-AI-001 §2.1）：一个后端语言、一个数据库、一个入口、一个 AI 出口、离线可还原。
2. **项目目录结构**（§7.1）与**中央包管理**（§7.3）：`Domain/Application/Infrastructure/Api` 四层照建，`Directory.Packages.props` 照用。层数不是微服务，四层是文件组织方式，小系统一样省不掉。
3. **离线四件套**中按技术栈适用的部分（§6.2）：`global.json`、`nuget.config`、`.editorconfig` 必备；前端存在时 `package-lock.json` + `.nvmrc` 必备（Python 侧车不存在时 `requirements.txt` 的豁免见 §5）。
4. **SQL 参数化、禁止拼接**；**禁止 `SELECT *` 进生产代码**；**密钥不进 Git、不进日志、不下发前端**；**CI 必须过 gitleaks**（§8.1 第 7、9、10 条）。
5. **鉴权与越权防护**：RBAC + 数据范围过滤 + 按 id 访问时服务端二次校验。**"都是自己人"不是理由**——内网系统最常见的泄露不是被黑客打下，而是同事随手改 URL 看到了不该看的工资/报价。
6. **结构化日志 + TraceId 贯穿**（含出站调用），出问题能追一次请求。
7. **`/health/live`、`/health/ready` 端点 + `deploy.ps1` + 30 秒内可回滚**。
8. **数据库迁移脚本入库、可重复执行**。
9. **备份真实存在且被验证过**：档位可以放宽"多久演练一次"（§3），但**不能放宽"上线前至少做过一次恢复"**。没验证过的备份等于没有备份。
10. **核心逻辑有单测**：状态机、金额/进度卷积、权限判定、导出这四类必测（不要求覆盖率百分比，要求覆盖判断点）。
11. **数据分级判定**（§10.1）与审计留痕 180 天：定级和留痕期不因系统小而下调。
12. **PR 检查清单**（§8.3）逐条打勾，AI 生成代码同样走 PR。

> 记忆口诀：**栈不许变、安全不许降、可回滚不许省、证据不许缺。**

## 3. 分档裁剪矩阵（核心表）

| 裁剪项 | S 档处理 | M 档处理 | L 档处理 | 依据 / 说明 |
|---|---|---|---|---|
| **Garnet（缓存）** | **不装**，只用 `IMemoryCache` | 按需装（出现跨进程共享、限流计数、分布式锁时） | 必装 + 监控告警 | §3.3 原文即"单机优先 IMemoryCache，确需跨进程共享再用"。单实例下装 Garnet 是纯增运维对象 |
| **Python 侧车** | 无 AI 需求 → **不装** | 有模型相关职责时装 | 装 | §3.5 职责限定为训练/推理/文档解析三类，没有就不装 |
| **AiGateway** | 不涉及 | 必须经它 | 必须经它 + 配额计费 | §2.1 铁律 4、§3.6 |
| **Ollama / 本地模型** | 不装 | 按 GPU 预算装 | 按 GPU 预算装 | §4.4、§3.7 |
| **微服务 / MQ / K8s / GraphQL** | 禁 | 禁（确需走 ADR） | 禁（确需走 ADR） | §8.1 第 5 条。**S 档连 ADR 都不必提，因为答案是明确的"不做"** |
| **容器（Docker）** | 禁 | 禁 | 禁（v1.x 一致） | §5 |
| **应用实例数** | 1（同进程承载 Web + 后台任务） | 1–2 | ≥2，Nginx 蓝绿 | §4.5 切换窗口说明 |
| **SQL Server `max server memory`** | **必设**（按物理内存约 70% 或显式上限） | 必设 | 必设 | §4.4 明确警示：单机第一杀手不是 CPU 而是内存。**这一条与系统大小无关，越是小机器越要设** |
| **Always On / 主从复制** | 不需要 | 不需要（用备份 + 恢复演练） | 评估 | 单机部署无副本前提 |
| **数据库日志备份频率** | 每日 1 次（随全备窗口） | 每小时 | 每小时 | §11 |
| **全备保留** | 14 天 | 30 天 | 30 天 | §11 |
| **RPO / RTO** | ≤ 24 h / ≤ 8 h | ≤ 1 h / ≤ 4 h | ≤ 15 min / ≤ 1 h | S 档放宽需业务方在验收单上签字确认 |
| **恢复演练频次** | 上线前 1 次 + 每年 1 次 | 每半年 | 每季度 | §11。**"上线前至少一次"不可裁** |
| **审计留痕时长** | 180 天（不降） | 180 天 | ≥ 180 天 | §10.2 |
| **Hangfire Dashboard** | 生产**不开放**（排障靠业务表 + 日志） | 生产不开放或强鉴权 | 强鉴权 | 官方文档警示：Job 参数与方法名会暴露，默认仅本地请求 |
| **压测范围** | 冒烟 + 基线 + 长跑 + 依赖故障，共 3–4 个场景（§4.1） | 全量场景 + 容量模型 | 全量 + 混沌 + 容量 | S 档目的是"证明不崩"，不是"找吞吐拐点" |
| **单测范围** | 状态机 / 卷积计算 / 权限判定 / 导出 四类必测 | + 用例全覆盖 | + 接口契约测试 | 不设覆盖率百分比门槛，设"判断点必须覆盖" |
| **OpenAPI 文档** | 开（仅内网，生产可关） | 开 | 开（限权） | §7.2 |
| **前端组件库** | Element Plus 不替换、不并存的约束**不变**；额外业务组件需登记 | 同 | 同 | §3.4、§8.1 第 4 条 |
| **依赖包白名单** | 仍逐个评审，但**同档已用过一次的包免二次评审**（见 §7） | 同 | 同 | §8.1 第 2 条。避免"每个项目重审一遍 Serilog" |

> 用法：在 README 的「裁剪声明」表（§7）里逐行写明"本项目 S 档 →  Garnet 不装 / 恢复演练每年一次 / RPO 24 小时"，评审人只看这张表和红线清单，不用重读整份基线。

## 4. S 档的简化边界：可以少做，不能不做

### 4.1 压测最低集（约半天，不可裁）

| 场景 | 目的 | 通过标准 |
|---|---|---|
| 基线 | 5 并发 × 10 min，混合只读主要页面 | 达到方案里声明的 P95 目标 |
| 长跑 | 2 并发 × 2–4 h | 进程工作集增长 < 20%（抓无界缓存键、DbContext 泄漏） |
| 依赖故障 | 防火墙阻断所有出站依赖（外部 API、SSO） | 主流程不崩、请求线程不阻塞、失败可观测、恢复后能自动补发 |
| 资源密集（如有导出/大列表） | 3 人并发触发导出 | 内存不超限、闸门生效、有明确拒绝提示 |

**明确不做的**：S 档不追求吞吐拐点、不做容量模型外推、不比较不同压测工具的绝对值。

### 4.2 性能与容量数字的口径要求（重要）

STD-AI-001 §0 摘要禁止编造数据，本指南补一条 S 档常见误用：

> **禁止把组件官方 benchmark 的数字当作本系统容量依据。** 官方基准通常在 72 vCPU / 144 GiB 这类与内网单机完全不同的环境下产出，且不同测试口径（`BenchmarkDotNet` 的托管堆累计分配 vs 进程 RSS 峰值）不可互相比较。S 档正确做法：**自己声明设计目标（附假设）→ 上线前实测 → 实测报告替代引用**。写不进实测的目标，就标注"待压测确认"，不要写成承诺值。

### 4.3 小系统真正的瓶颈排序（按实际发生概率）

| 排序 | 瓶颈 | 为什么小系统更容易中 | 对策 |
|---|---|---|---|
| 1 | **内存**（多进程抢 + SQL Server 不设上限） | 单机同机部署，没有余量 | 必设 `max server memory`；S 档主动**少装组件**（§3） |
| 2 | **全内存 DOM 型导出** | 业务量小 → 没人测导出上限，一次全量导出就打爆 | 行数硬上限 + 并发闸门 + 异步任务化 |
| 3 | **递归/树形查询写 N+1** | 代码量小、审查松 | 物化路径（`Path` 列）+ 一次查子树 |
| 4 | **无人使用导致的数据腐烂** | 部门级系统缺推广 | 见 §4.4 |
| 5 | 吞吐 / QPS | **几乎从来不是 S 档的瓶颈**（日请求量 < 5 万，平均 QPS < 1） | 不要为此引入缓存集群、读写分离 |

### 4.4 S 档反而要**加码**的三项（小系统的独特风险）

小系统失败的模式和大系统不同：**不是被打挂，是没人用；不是没人用，是人走了没人会改。** 因此以下三项要求比 M/L 更严：

| 加码项 | 具体要求 | 针对的风险 |
|---|---|---|
| **采用度指标** | 成功标准里必须写"上线满 30 天周活跃占比"之类的可数指标，并在系统内做一个管理员可见的活跃度页面；业务方验收单必须签字确认"有人在用"（§13 DoD 第 10 条） | 部门级工具半年后沦为无人更新的空表 |
| **接手成本证据** | README 必须写到"换一个人、断网、只给这台机器"能独立完成：取包 → 构建 → 部署 → 建库 → 备份恢复。并以一次**真实换人演练**（让别人照着 README 部署一遍）作为验收项 | 单点依赖原作者，人走即失控——这正是 STD-AI-001 §0 列出的第三个原始痛点 |
| **填报成本约束** | 凡需要业务方持续录入的功能，必须给出"完成一次填报 ≤ 2 次交互 / ≤ 30 秒"的设计约束，并优先用自动生成草稿再让人补充的形态 | 数据质量差 → 报表失真 → 管理层弃用，形成死亡螺旋 |

## 5. 交付物与离线锁文件按技术栈裁剪

§6.2「四样缺一不算交付」中的四件（`global.json`、`nuget.config`、`package-lock.json`/`.nvmrc`、`requirements.txt`）是按**全栈都用到**的假设写的。S 档常不引入 Python 侧车，此时应有针对性豁免，并在 README 登记：

| 锁文件 | 适用前提 | 不存在时的处理 |
|---|---|---|
| `global.json`、`nuget.config`、`Directory.Packages.props`、`.editorconfig` | 永远适用 | 无豁免 |
| `package-lock.json` + `.nvmrc`（或 `engines`） | 有前端时 | 纯 API 无前端 → 免，登记理由 |
| `requirements.txt` + `wheelhouse` | 有 Python 侧车时 | **无 AI 职责 → 免，登记理由**（建议提交一份 ADR 说明，或在本指南 §7 的免评审登记通道内处理） |
| 模型文件 SHA256 存档 | 有本地模型时 | 无模型 → 免 |

**文档可合并，不可省略**：S 档允许把 `offline-build.md` 与 `dr-drill.md` 合并为一份 `docs/verification.md`（构建验证 + 恢复演练两段），但两段内容都必须存在。`deploy.ps1`、`README.md`、迁移脚本、ADR 目录结构不得合并或省略。

## 6. 运行时出网 ≠ 构建期离线（易被误读，单列）

STD-AI-001 §1 前提假设是"内网完全断网或仅有限外网"，§2.1 铁律 5 是"离线可还原"。很多项目在此卡住：以为接钉钉/企业微信/OSS 之类的公网服务就违反了标准。**不是。**

> **铁律 5 约束的是构建期与部署期**（依赖可离线还原、断网机器能 `restore → build → publish → deploy`）；**运行期的出站网络访问是另一个维度**，不属于"偏离标准"，但属于**必须登记的安全变更**。

登记模板（写入项目 `README.md` 或独立 ADR）：

| 项 | 内容 |
|---|---|
| 出网站点 | `oapi.dingtalk.com:443`、`api.dingtalk.com:443`（**精确到域名，不开 `0.0.0.0/0`**） |
| 方向 | 仅出站；不开任何入站（尤其不开公网回调入口） |
| 触发场景 | 免登换取 userid、通讯录定时拉取、工作通知推送 |
| 依赖强度 | 非核心链路（钉钉不可用不得阻塞业务主流程） |
| 降级路径 | Adapter 熔断 → 会话延续不强制重登 → 通知落库待发送、恢复后按退避补发 → 页面横幅兜底 |
| 凭据位置 | `D:\Secrets\{app}.json`，ACL 只给服务账号，部署时注入环境变量 |
| 前置检查项 | ① 开放平台「服务器出口 IP 白名单」已登记真实公网出口 IP（未登记会导致接口全部返回 `invalid ip`）；② 服务器时间与 NTP 偏差 < 15 分钟（偏差过大会导致签名失效） |
| 审批 | 架构负责人 + IT 运维（防火墙出站规则） |

**内网系统不接公网回调**：外部平台的"事件订阅/回调"能力需要公网可达地址。内网系统默认**放弃事件订阅，改用定时拉取**，理由是避免为此在 DMZ 开入口（扩大攻击面），而拉取模式的数据新鲜度对部门级系统足够。此判定建议记为 ADR。

## 7. 裁剪声明登记（替代 ADR 通胀）

### 7.1 三档审批口径

| 情形 | 处理方式 | 谁批 |
|---|---|---|
| **档内裁剪**：按 §3 矩阵在所属档位内执行（如 S 档不装 Garnet、恢复演练每年一次） | **免 ADR**，在项目 README「裁剪声明」表登记一行即可 | 项目负责人自签，评审会扫一眼 |
| **偏离基线**：标准明确禁止项要做（引入第二个数据库 / 容器 / 微服务 / 直连模型 / 未评审包），或**提前引入高档组件**（S 档却要装 Garnet） | **必须走 ADR**，按 `docs/adr/0000-adr-template.md` | 架构负责人签字 |
| **不确定属于哪类** | **先问，不要先做了再说**（§2.2 治理原则） | — |

### 7.2 README 裁剪声明表模板（直接复制到项目 README）

```markdown
## 规模定档与裁剪声明

- **定档**：S 档
- **判据**：注册用户 20；峰值并发 ≤ 6；无模型调用；不写回外部生产库；单实例可接受停机
- **定档日期 / 定档人**：2026-10-27 / @张三
```

## 8. 升档复核：什么时候 S 档假设会失效

**任一命中，立即按 §1 重新定档**，不要在 S 档配置上继续打补丁：

| 触发条件 | 典型征兆 | 要补的动作 |
|---|---|---|
| 用户 > 50 或峰值并发 > 10 | 列表页 P95 从 200 ms 涨到 1 s+ | 重估索引、分页、快照预聚合 |
| **实例数 ≥ 2**（横向扩容 / 零停机） | 想再加一个进程分担任务 | **补 Garnet**：会话与凭证需共享，钉钉类 Token 多实例各自刷新会互相顶掉（典型故障：偶发 token 失效、重启后好一阵又复发）。→ 这正是升档最常见的第一个技术后果 |
| 引入任何模型调用 | 加了个"智能问答"按钮 | 补 Python 侧车 + AiGateway + 数据分级评估 + Prompt 审计留痕，并写 ADR |
| 需要写回外部生产库 | 要把计划同步进 ERP | 补 Adapter、中间表 + 审批、对账机制、数据一致性设计 → 定 L 档 |
| 单库 > 5 GB 或核心表行数进入千万级 | 备份窗口超时、查询计划劣化 | 补归档策略、索引维护作业、分区评估 |
| 出现跨进程锁 / 抢任务 | 两个 Job 重复处理同一批数据 | 补分布式锁（Garnet）或让 Hangfire 承担（它自带分布式锁与 at-least-once 语义，先判断是不是 Job 没做幂等） |
| 业务要求 RPO < 4 小时 | 数据被下游依赖、丢一天要出事 | 日志备份改每小时，重演 RTO 演练 |

> **升档是"补装"，不是"重构"。** 前提：抽象层和目录结构从一开始就按标准走。代码只依赖 `IDistributedCache`，S→M 装 Garnet 是加一个 Provider 加一行配置；反之，一开始随手 `Dictionary` 存缓存、把配置硬编码进代码的项目，升档必然重写。**这才是统一模板真正的回报**——它不是为了让代码长得一样，是为了让"变大"这件事的成本可控。

## 9. 示范：一个 S 档系统的完整定档与裁剪

| 项 | 内容 |
|---|---|
| 系统 | 部门内部计划管理系统（计划台账 / 任务 / 进度 / 看板 / 甘特 / 人力负荷 / 周日报 / 钉钉集成） |
| 判据实测 | 用户 20；峰值并发 ≤ 6；日请求约 720（人均 40 次），平均 QPS ≈ 0.1，容量上限按 3 QPS 设计；3 年数据量估算 ≈ 120 MB；无模型调用；不写回外部生产库；单实例可接受 < 30 秒停机 |
| **定档** | **S 档** |
| 组件裁剪 | Nginx + 1 个 ASP.NET Core 应用（同进程承载 API 与 Hangfire Worker）+ SQL Server 一个独立库。**不装 Garnet、不装 Python 侧车、不装 AiGateway、不装 Ollama、不上容器、不上 MQ** —— 相比照抄基线少 4 个常驻进程 |
| 备份裁剪 | 每日全备（01:00）+ 每日日志备份，全备保留 14 天；RPO ≤ 24 h / RTO ≤ 8 h，由业务方在验收单签字 |
| 演练 | 上线前做一次真实恢复到测试实例；之后每年一次 |
| 压测 | 基线 / 长跑 4 h / 出站依赖故障 / 并发导出 共 4 个场景，报告并入 `docs/verification.md` |
| 出网登记 | 仅 `oapi.dingtalk.com:443`、`api.dingtalk.com:443` 出站；**放弃事件订阅，改定时拉取**（记 ADR）；开放平台出口 IP 白名单与 NTP 偏差列为部署单强制检查项 |
| 反而加码 | ① 周活跃 ≥ 90% 与任务进度周更新率 ≥ 85% 两个采用度指标做成系统内可见页面；② 验收含一次"换人照 README 断网部署"演练；③ 周日报草稿由系统自动生成，人只补总结（≤ 2 次交互完成填报） |
| 需写 ADR 的部分 | 出网白名单（安全变更）、放弃事件订阅、新增 vxe-gantt 等业务组件到包白名单、业务日期用 `date` 而非 `datetime2 UTC`（与 §9 时间规范的关系澄清）、无 Python 时 `requirements.txt` 豁免 |
| 免 ADR 的部分 | 不装 Garnet / 不装 Python 侧车 / 备份与演练频次放宽 / RPO-RTO 放宽 —— 全部属 §3 矩阵 S 列，登记一行即可 |

## 10. 评审检查口径（给评审人）

对着这三问看，10 秒判完，不必重读基线：

1. **定档了吗？** README 顶部有没有「定档 + 判据（可数的量）+ 定档人」。没有 → 打回，不进入内容评审。
2. **裁剪在矩阵内还是矩阵外？** 在 §3 的列里 → 登记即可；在列外（要装高档组件、要做标准禁止的事）→ 有没有对应 ADR。
3. **红线有没有被"小"字绕过？** 对照 §2 十二项逐条打勾。凡出现"内部小系统就不用 / 就我们几个人 / 以后再说"的表述，一律要求补齐或补 ADR。

补充关注点（本类项目高频问题）：`max server memory` 是否设了；导出有没有行数与并发闸门；按 id 访问有没有服务端二次鉴权；有没有把组件 benchmark 当容量承诺；恢复演练是不是"做过且留了记录"。
